# Vision — Видение проекта

> Файл описывает общее видение, цели и принципы проекта. Технические детали — в `arch.md`.
> Спецификация внешнего API брокера БКС — в `BCS-SPEC.md`.

## 1. Идея в одном предложении

Собственная многоброкерская инвестиционная платформа: единый веб-клиент, который показывает
портфель, котировки и торговые данные сразу от нескольких брокеров, через набор независимых
микросерверов-адаптеров.

## 2. Зачем это нужно

### 2.1 Практическая цель
У большинства частных инвесторов счета разбросаны по разным брокерам (БКС, Т-Инвестиции,
Газпромбанк, ВТБ, Сбер). У каждого брокера своё приложение и свой API. Хочется:

- **единую картину** — все активы, позиции и суммарный капитал в одном интерфейсе;
- **независимость от брокера** — свой UI, свои алерты, свои расчёты (доходность, allocation);
- **историчность** — брокеры не хранят историю котировок и снимков портфеля для клиента;
  собственный сервер данных позволит копить историю и строить графики/аналитику;
- **безопасность ключей** — refresh-токены брокеров хранятся на своих серверах, а не в браузере.

### 2.2 Образовательная цель
Проект создаётся в том числе как полигон для изучения технологий. Каждый сервис пишется
на языке/фреймворке, который интересно освоить: TypeScript + Fastify, Python, Go,
Java Spring. Это осознанное усложнение: разнообразие стеков заставляет продумывать
межсервисные контракты, формат обмена и деплой лучше, чем в монолите на одном языке.

## 3. Ключевые принципы

1. **Единый контракт для клиента.** Веб-клиент не знает, какой брокер отвечает. Все
   брокерские серверы реализуют один и тот же внутренний REST-контракт (`/api/v1/...`):
   одинаковые пути, одинаковые JSON-схемы ответов, одинаковые ошибки. Добавить нового
   брокера = написать новый сервер-адаптер, клиент не меняется.
2. **Тонкие адаптеры, умный контракт.** Вся «грязь» конкретного брокерского API
   (форматы токенов, пагинация, коды ошибок) остаётся внутри его сервера. Наружу —
   только нормализованные данные нашей модели.
3. **Один брокер — один сервис.** Серверы изолированы: падение или деградация одного
   брокера не влияет на остальных. Язык, база, деплой — у каждого свои.
4. **Данные рынка — общий ресурс.** Отдельный сервер данных (Java Spring) кэширует
   котировки/свечи и раздаёт их остальным сервисам и клиенту. Остальные серверы
   обращаются к нему за историей и онлайн-данными, а не дублируют их.
5. **MVP — минимальная вертикаль.** Первый рабочий срез: клиент → bcs-server → БКС API →
   отображение портфеля. Всё остальное наращивается итеративно поверх того же контракта.

## 4. Что входит в продукт (по стадиям)

| Стадия | Содержание |
|--------|-----------|
| MVP | bcs-server (Fastify) + React-клиент: просмотр портфеля БКС по refresh-токену |
| v0.2 | Единый контракт зафиксирован; второй брокер (например, Т-Инвестиции, Python) |
| v0.3 | Сервер данных (Spring): сбор/кэш котировок, история цен в БД |
| v0.4 | Мультиброкерский дашборд: агрегация портфелей, суммарный капитал |
| v1.0+ | Уведомления, аналитика доходности, история позиций, стриминг обновлений |

## 5. Нецели (осознанно вне скоупа)

- Автоторговля и исполнение заявок — пока только чтение данных (write-endpoints могут
  появиться далеко за MVP, и никогда из браузера напрямую).
- Хранение денег/персональных данных клиентов третьих лиц — платформа для себя,
  single-user на первом этапе.
- Повторение функциональности брокерских приложений (пополнение, ввод-вывод, налоги).

## 6. Ожидаемый результат

Через несколько месяцев — работающий личный кабинет инвестора: открываешь свой фронт,
видишь консолидированный портфель по всем брокерам, графики по накопленной истории цен,
при этом каждый backend-сервис — отдельная учебная лаборатория со своим языком и своим
стеком, объединённые одним API-контрактом.
